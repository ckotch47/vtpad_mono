## Общие требования

- Сохранять tenancy: каждый REST/MCP запрос и каждая связь/lookup ограничены тем же `space`; cross-space объекты не раскрываются.
- Каждая новая операция, доступная через backend REST, имеет функционально эквивалентный MCP tool с теми же входными проверками, статусами и результатом. Обновлять MCP schemas/описания и endpoint map.
- Учитывать уже существующие данные и snapshots. Не трактовать `NULL` как 0 и не менять исторический состав run.
- Каждая миграция идемпотентна и проверяется на восстановленной disposable-копии БД. Производственную/основную БД использовать для проверок только read-only; запрещено изменять её данные тестовыми запросами.
- Изменения backend/frontend сопровождаются релевантными обновлениями `project-docs/docs/`, `ROADMAP.md` и статусом соответствующего плана. Новая зависимость допускается только при необходимости с обновлением dependency docs.
- После каждого вертикального пакета: targeted lint/type/static checks, production build, REST+MCP contract check, изолированный runtime smoke, desktop/mobile UI smoke по scope; `git diff --check`; отдельный коммит.
- В конце пересобрать/перезапустить локальные сервисы VTPad и подтвердить health endpoints, UI, миграционный ledger и ключевые сценарии на disposable DB. Оставить локальный сервис доступным.

## Этап 2 — общие UX-улучшения

### UX1. Cmd/Ctrl+S и Esc

Реализовать scoped keyboard shortcuts: Cmd/Ctrl+S вызывает существующее сохранение только в активном редактируемом форме; не перехватывать текстовый ввод/браузерные поля. Esc закрывает верхний modal/dialog только когда форма не находится в состоянии подтверждения/сохранения; unsaved changes используют уже существующий confirm flow или явное предупреждение.

### UX2. Skeleton таблиц

Добавить общий переиспользуемый skeleton для initial load основных таблиц cases, suites, runs, plans, bugs и tech docs; удерживать высоту, не скрывать доступные фильтры и не заменять существующий контент при фоновом обновлении.

### UX3. Empty states

Для основных списков оформить отдельные состояния: первоначально пусто, нет результатов фильтра, ошибка загрузки и нет прав. Показать понятный CTA Create/Clear/Retry только при доступных правах; CTA должен работать с клавиатуры.

### UX4. Mobile responsiveness

Провести аудит критических flows по `project-docs/docs/ops/ui-regression-full-checklist.md`: suite/case, test plan, run/result, bugs, analytics, tech docs. Исправить overflow toolbar/table/editor/dialog, проверить touch targets, zoom/reflow, focus и back navigation на малом viewport.

## Этап 3 — backend search и обмен данными

### BD1. PostgreSQL full-text search

Добавить транзакционно обновляемый `tsvector` и GIN индекс для согласованного текста testcase и suite; использовать PostgreSQL `simple` config для русско- и англоязычных запросов без неподтверждённого стемминга. Использовать параметризованный `websearch_to_tsquery`, ranking с устойчивым tie-break и space/permission filters. Пустой запрос сохраняет прежний список; существующие фильтры/пагинация совместимы. Эквивалентный поиск доступен через REST и MCP.

### BD2. CSV/JSON import/export suites и cases

Экспортировать suites, секции и cases в JSON и CSV; экспорт не включает run history, пользователей и секреты. JSON сохраняет иерархию и typed fields; CSV представляет секцию полным путём. При импорте генерировать новые ID, не подменять существующие UUID и не переносить историю версий/run. Перед записью выдавать preview с ошибками по строкам. Импорт атомарный: дубликат имени/short name или некорректная ссылка делает preview невалидным и не создаёт частичную запись. Проверять размер/MIME, membership, допустимые поля и связи; функции доступны через REST и MCP (для файлового MCP использовать тот же content schema, не filesystem path).

## Этап 4 — custom fields, plans и analytics

### FI5. Значения пользовательских полей case

Завершить имеющиеся `custom_field`/value CRUD: встроить typed values в case view/edit, валидировать тип, обязательность, принадлежность поля тому же space и права. Сохранять историческое значение в testcase version/run snapshot; удаление или смена типа поля не ломает старые версии. Поля доступны через REST и MCP.

### FI1. Расширенные фильтры Test Plan

В форму Test Plan добавить пересекающиеся фильтры по SU8 tags/priority и FI5 typed custom fields, серверный preview с counts и тем же query, что используется при создании. Snapshot план/run фиксирует выбранные кейсы; последующие изменения tags/custom fields не меняют старый run. REST/MCP preview и создание используют общую бизнес-логику.

### AN1. Дополнительная аналитика

Добавить два конкретных вопроса поверх существующего dashboard: (1) какие suites имеют растущую долю failed результатов по периодам; (2) какие cases повторно падают в последних runs. Для каждого показывать период, знаменатель/coverage, фильтры, пустое состояние и drill-down к suite/case/run. Статистика использует только доступные пользователю данные того же space, snapshots и детерминированные границы периода. Новые API доступны REST/MCP.

### AN2. Аналитика времени

Показывать по периодам/сuites оценочное время набора run, сумму измеренного case time и active run timer отдельно; paused time не входит в active, unmeasured cases исключаются из среднего и отражаются coverage. Исторические snapshots используют оценку на момент run. Графики и агрегаты сверяются с run detail/history на контрольных данных; REST и MCP возвращают одинаковые агрегаты.

По умолчанию создание не происходит; обычный run остаётся закрытым. Публичный endpoint не поддерживает list/search/mutation и не принимает токен в логируемом query string.
