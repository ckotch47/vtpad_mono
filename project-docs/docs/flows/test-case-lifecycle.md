# Жизненный цикл test case и checklist

Test cases и checklists используют общую запись и существующие страницы библиотеки. Тип определяет только применимое представление:

- **Manual case** показывает описание, предусловия, шаги и ожидаемые результаты.
- **Checklist** показывает описание и checks, сохранённые в общем поле `steps`. Предусловия и ожидаемые результаты в интерфейсе checklist скрыты.
- **Automated case** сохраняет прежний набор полей и поведение.

## Шаблоны кейсов

В списке Test Cases действие **Case Templates** открывает управление шаблонами текущего space. Шаблон имеет отдельное имя и неизменяемые numbered versions; изменение content добавляет новую версию, а изменение только metadata не переписывает существующие версии. В content входят default case title, description, preconditions, steps, expected results, postconditions, type, priority и estimate. Tags и custom-field values в шаблон не копируются.

В create-case форме можно выбрать шаблон. UI получает текущую версию и копирует её разрешённые поля в обычный draft кейса; если пользователь ещё не вводил title, он получает default title шаблона. Перед сохранением пользователь может проверить и изменить draft. Создание кейса остаётся стандартным create flow; кейс не хранит ссылку на источник. Поэтому дальнейшее изменение шаблона не меняет созданные кейсы.

В форме редактирования переключение типа скрывает неприменимые поля, но не очищает их. Сохранение отправляет значения общей записи; при возвращении к прежнему типу они снова доступны. Создание checklist также использует стандартный rich-text редактор и общую модель testcase.

Версии testcase и новые test run продолжают использовать существующие version snapshots. В run detail checklist открывается из snapshot конкретного результата, поэтому редактирование testcase после старта запуска не подменяет его checks. Для legacy результатов без snapshot остаются доступными только поля, которые предоставляет legacy ответ.

Выполнение checklist имеет один статус на весь testcase result. Строки checks являются инструкцией для проверки и не получают отдельного сохранённого статуса.

## Перемещение между suite и sections

Для явного переноса testcase используется `POST /api/v2/test-case/{testcase_id}/move` с обязательными `suite_id` и `section_id`. `section_id: null` означает виртуальную секцию `Default` выбранного suite. MCP сохраняет прежний `move_test_case(case_id, suite_id=None, section_id=None)` с legacy partial-update поведением и ответом для существующих клиентов. Для нового явного контракта используйте `move_test_case_to_location(case_id, suite_id, section_id)`; оба destination-параметра обязательны, а для `Default` передавайте `section_id: null`. Новый MCP tool и REST вызывают общий сервис: suite и section должны находиться в space кейса, а section — принадлежать destination suite. Отсутствующая или чужая space-ссылка возвращает общий `404`; section другого suite в том же space возвращает `422`. Перемещение меняет только расположение, не создаёт content version; счётчики suites/sections остаются производными от фактического размещения кейсов. Повторное перемещение в ту же локацию успешно и не меняет запись.

Полнотекстовый поиск cases/suites использует PostgreSQL vectors с `simple` конфигурацией и GIN indexes. `BEFORE`-триггеры пересчитывают vectors в той же транзакции, что и insert/update исходных полей, включая прямые SQL и будущий import. Если полный vector превысил бы PostgreSQL limit 1 MiB, builder повторяет индексирование с первыми 8 192 символами каждого поля, чтобы сохранить запись. Непустой поисковый запрос параметризуется через `websearch_to_tsquery`; для кейса точное совпадение short name также находит hyphenated identifiers вроде `TC-123`; выдача сортируется по релевантности и затем по ID. Пустой/пробельный запрос возвращает обычную сортировку списка. Индексация и filters всегда ограничены целевым space; REST и MCP проверки доступа для списка suites одинаковы.

В деталях suite у каждого testcase есть действие «Переместить в другой раздел». Диалог предлагает `Default` и sections текущего suite, блокирует повторный submit и показывает ошибку API для повторной попытки. После успеха список, счётчики и выбранный destination обновляются. Add-to-suite из списка существующих кейсов по-прежнему сохраняет прежний flow.

В fixed-top меню rich-text редактора кнопки переносятся на следующие строки; меню ограничено высотой 96 px и прокручивается внутри себя. Это сохраняет рабочую область редактора видимой при редактировании длинных testcase.

## Приоритеты, метки и версии

У кейса есть приоритет `P0`–`P3` (по умолчанию `P2`) и набор меток, принадлежащий его space. Метки обрезаются по краям, сравниваются без учёта регистра и дедуплицируются внутри space. В списке можно фильтровать по приоритету и нескольким меткам одновременно: кейс должен иметь все выбранные метки. PATCH без `tags` сохраняет набор, `tags: []` очищает его.

Новые версии фиксируют `type`, priority и текстовые значения меток вместе с остальным содержимым. В исторических версиях, созданных до этой схемы, эти поля остаются неизвестными (`null`); восстановление такой версии сохраняет текущие неизвестные поля. Новый test run копирует priority и метки в неизменяемый snapshot результата.

Testcase custom fields имеют тип `text`, `select`, `multiselect`, `number`, `date` или `checkbox`. Для select и multiselect требуется хотя бы один уникальный непустой вариант; сохранённое значение должно совпадать с вариантом. Числа не принимают boolean/NaN/Infinity, даты должны быть ISO-датой, а checkbox принимает только boolean. `required` по умолчанию выключен и доступен только для testcase. До включения обязательности поле должно быть заполнено у всех существующих cases; при создании case каждое required поле должно иметь значение. REST и MCP передают значения как `custom_fields: [{field_id, value}]`; PATCH без ключа сохраняет текущие значения, переданный массив полностью заменяет набор. Все операции проверяют field, entity и доступ в одном space; REST и MCP `set_custom_field_value` возвращают новое сохранённое значение. Detail и list/search ответы REST и MCP `get_test_case`/`search_test_cases` включают метаданные и значения; коллекции загружают их пакетно, а не отдельным запросом на каждый case.

Операции создания/дублирования testcase и создания/включения required custom field синхронизируются блокировкой строки space, чтобы конкурентная операция не пропустила обязательное поле. Восстановление версии блокирует определения полей перед проверкой и записью snapshot values, сохраняя порядок блокировок testcase → fields. Постоянное удаление testcase удаляет его testcase custom-field values в той же транзакции; testcase, сохранённый в истории run, переводится в `deprecated` и сохраняется вместе со значениями.

Testcase detail/edit показывает пользовательские поля. Каждая новая версия копирует значения вместе с именем, типом, вариантами и required-флагом. Новые run результаты копируют эти данные в JSON snapshot. Поэтому удаление definition или смена его типа не меняет старые версии и созданные runs. Legacy snapshots без `custom_fields` показывают неизвестную историю, а не значения текущего testcase. При восстановлении старой версии удалённые или несовместимые определения пропускаются; обязательные текущие поля не очищаются.

На странице testcase можно выбрать две сохранённые версии независимо и сравнить их на одной странице. Сравнение включает title, type, priority, tags, custom fields, description, preconditions, упорядоченные steps и expected results. Шаги сопоставляются по общей последовательности, чтобы вставки и удаления в середине списка не сдвигали остальные строки; замена шага без совпадающей строки показывается удалением и добавлением. Вложенные пункты rich text остаются частью родительского шага. Старые snapshots с отсутствующими type/priority/tags/custom fields показывают `Unknown (legacy snapshot)`. Rich text очищается перед выводом. Действие восстановления версии B создаёт новую версию, не перезаписывая историю.

В формах создания testcase, test plan и test run, а также в редактировании testcase и Tech Docs сочетание Cmd/Ctrl+S запускает существующее действие сохранения активной формы. В полях поиска и вне отмеченной формы сочетание остаётся браузерному действию. Esc закрывает верхний Vuetify overlay; если форма содержит изменённые данные, перед закрытием показывается подтверждение, а во время отправки запроса overlay остаётся открытым. Run result и quick bug dialogs используют тот же контракт.
