# Планы решений по ROADMAP.md — r1

Дата сверки: 2026-10-08. Источник: текущий `ROADMAP.md` и код в рабочей копии. Это планы, а не подтверждение работающего поведения: UI и интеграционные сценарии не запускались. Реализация каждого пакета требует отдельного согласования точной ревизии плана по `AGENTS.md`.

## Правила для всех пунктов

- Данные всегда ограничены `space`; новый API проверяет членство пользователя и принадлежность всех связанных объектов. Для данных истории используется snapshot на момент создания run, а не меняющийся текущий кейс.
- Миграции должны сохранять старые записи: новые необязательные поля остаются `NULL`, а отсутствие замера не отображается как ноль.
- При изменении кода одновременно обновляются соответствующие страницы `project-docs/docs/` (API, flows, architecture, rules либо errors). Критерии ниже включают проверку доступа, старых данных и ошибок.
- Статусы: **нет** — функция не найдена; **частично** — имеется часть контракта или UI; **есть по коду** — реализация найдена, нужна проверка сценария перед закрытием roadmap; **реализовано (код)** — согласованный пакет закоммичен и документация обновлена, но runtime-проверка могла не выполняться.

## 1. Test Execution Time

### TE1. Оценочное время кейса — реализовано (код, r2)

**Основание:** `vtpad_backend/app/src/test_case/model.py` не содержит оценки. **Решение:** добавить nullable `estimated_duration_seconds >= 0` в кейс и версию, миграцию, DTO/ответы API и поле редактора; при создании run копировать оценку в snapshot результата. **Приёмка:** оценка редактируется и сохраняется; изменение исходного кейса не меняет старый run; старый кейс без оценки остаётся доступным. **Зависимость:** базовый контракт времени для TE2–TE5 и AN2.

### TE2. Фактическое время кейса в прогоне — реализовано (код, r2)

**Основание:** `TestResultModel.duration_seconds` уже существовало, но ввод и отображение были неполными. **Реализация r2:** фактическая длительность вводится/редактируется вручную, валидируется как неотрицательное число и показывается отдельно от `NULL`; `0` — допустимое значение. Автоматический секундомер на каждый кейс не входит в r2. **Приёмка по коду:** DTO/MCP отклоняют отрицательные значения; UI различает ноль и отсутствие замера.

### TE3. Сумма времени кейсов для run — реализовано (код, r2)

**Основание:** `test_run/service.py` возвращает статусы результатов, но не сумму; `RunStatsPanel.vue` её не показывает. **Решение:** сервер считает сумму известных `duration_seconds` результатов run и число результатов без замера; detail API и панель показывают оба числа. **Приёмка:** сумма совпадает с результатами после правки/удаления времени; неизвестные значения не выдаются за измеренный ноль. **Зависимость:** TE2.

### TE4. Таймер run с паузой — реализовано (код, r2)

**Основание:** до r2 у run были только `started_at/completed_at`. **Решение r2:** таймер общий для run; интервалы хранятся на сервере, а время вычисляется при API-запросе. Start/pause/resume/complete транзакционны; уникальный частичный индекс ограничивает run одним открытым интервалом. Нет cron, фонового цикла или клиентского секундного интервала. Legacy run без интервалов показываются как untracked; pause/resume для них отклоняются. **Приёмка по коду:** состояние восстанавливается из API, паузы исключены из активного времени, переходы доступны в REST и MCP.

### TE5. Длительность и детали времени в истории — реализовано (код, r2)

**Основание:** ранее история кейса показывала только `duration_seconds`. **Реализация r2:** история отображает фактическое время кейса и доступные календарное/активное/паузное время run. REST и MCP отдают одни timing-поля; старые run без интервалов показывают отсутствие замера активного и паузного времени. Snapshot кейса сохраняет оценку на момент создания run.

## 2. Run Navigation

### RN1. Группы кейсов по папкам и секциям — реализовано (код, пакет RN r1)

**Реализация:** preview и создание run используют один вычисленный snapshot с suite и root→leaf `section_path` (`id/name/sort`); путь включён в selection hash. Перед возвратом location проверяется, что suite и каждый section принадлежат space кейса и той же suite. Run detail группирует результаты по suite и пути; старые snapshots используют известную leaf section, legacy results — только доступный текущий путь. **Приёмка по коду:** вложенный путь и порядок сериализуются; фильтр не смешивает suites; переходы по группам учитывают фильтр. Runtime переименование/перенос и legacy сценарии не запускались.

### RN2. Быстрый переход между группами — реализовано (код, пакет RN r1)

**Реализация:** desktop имеет соседнюю sticky-навигацию, mobile — горизонтально прокручиваемые кнопки; список и счётчики вычисляются после фильтрации, переход прокручивает и фокусирует доступный заголовок группы. `Next not run` сохранён. **Приёмка по коду:** ESLint/build прошли; ручная keyboard/mobile проверка в браузере остаётся.

## 3. Suite and Case UX

### SU1. Список suites слева и выбранная suite на той же странице — нет

**Основание:** `pages/space/:spaceId/test-suites/index.vue` и `:suiteId.vue` — отдельные экраны. **Решение:** общий split layout на index с переиспользованием detail; выбранную suite хранить в URL, на мобильном показывать одну панель. **Приёмка:** прямой URL, Back/Forward, выбор другой suite, пустой/ошибочный ответ и фокус работают без сброса состояния.

### SU2. Исправить фильтр кейсов в suite — частично, вероятный дефект

**Основание:** `SuiteCasesPanel.vue` передаёт поиск, `useTestSuiteDetail.js` вызывает `.toLowerCase()` у значения clearable input и фильтрует лишь загруженную секцию. **Решение:** сначала воспроизвести сбой при очистке, нормализовать `null` к строке; определить область поиска (текущая секция или вся suite) и при необходимости перевести на серверный поиск. Разделить состояния «нет кейсов» и «нет совпадений». **Приёмка:** ввод, очистка, смена секции, регистр, пагинация и пустой ответ работают. **Зависимость:** решение об области поиска.

### SU3. Дерево suites в стиле Tech Docs — нет, нужен UX-выбор

**Основание:** `TechDocSidebar.vue` имеет дерево и поиск; `TestSuiteModel` имеет `sort`, но не родителя. **Решение:** сделать прототип навигационного дерева/списка для SU1 с поиском, счётчиками и архивом. Если нужна именно вложенность suites, отдельно спроектировать `parent_id`, миграцию, ограничения циклов и API; иначе переиспользовать плоскую навигацию. **Приёмка:** прототип проверен на большом списке и мобильном экране; выбранная модель и её границы зафиксированы до изменения БД.

### SU4. Перетаскивание секций — частично

**Основание:** поле `SectionModel.sort` и sort endpoint есть, drag UI нет; существующий sort требует проверки общего parent. **Решение:** сначала ограничить reorder соседними секциями и проверить parent на сервере, затем добавить drag с клавиатурными действиями и откатом UI при ошибке. Перенос между родителями проектировать отдельно. **Приёмка:** порядок сохраняется после reload; нельзя переупорядочить чужую suite, создать цикл или нарушить вложенность.

### SU5. Поиск и фильтр дерева секций — нет

**Основание:** `SuiteSectionsPanel.vue` выводит весь `flatSections` без query. **Решение:** поиск по имени с показом предков совпавших узлов, очисткой и отдельным empty state; выбранную секцию не терять. **Приёмка:** вложенное совпадение видно в контексте пути, длинные имена и клавиатурная навигация доступны.

### SU6. Перенос кейсов между секциями — частично

**Основание:** перенос в Default и добавление существующих кейсов уже есть в `SuiteCasesPanel.vue`/`useTestSuiteDetail.js`. **Решение:** первым этапом добавить явное Move с диалогом выбора suite/section и подтверждением; сервер проверяет принадлежность space и допустимость назначения, затем обновляет counts и список. Drag можно добавить позже поверх того же API. **Приёмка:** перенос между секциями и в Default, отмена, ошибки и reload не теряют кейс.

### SU7. Сравнение двух версий кейса — частично

**Основание:** `testCaseDetailComponent.vue` показывает current и одну выбранную историческую версию. **Решение:** два независимых селектора версий, структурное сравнение полей и шагов через имеющийся version/diff API после проверки контракта; rich text показывать безопасно. **Приёмка:** две произвольные версии, одинаковые версии, старые неполные snapshots и длинные поля читаются и дают правильный diff.

### SU8. Теги и приоритет кейсов с поиском/фильтрами — нет

**Основание:** `TestCaseModel`/DTO не имеют priority/tags, а list UI фильтрует type/status/suite. **Решение:** определить enum/справочник приоритетов и space-scoped теги; добавить миграцию, API, версионирование, индекс/поиск, редактор и URL-синхронизированные фильтры. **Приёмка:** комбинации тегов и приоритета, очистка, пагинация, старые кейсы и права дают стабильный результат. Этот пункт — предпосылка FI1.

## 4. Test Cases and Checklists

### TC1. Разные представления — нет

**Основание:** type уже есть, но `testCasesListComponent.vue` и редактор кейса используют общий набор полей, включая expected results для checklist. **Решение:** сохранить общий data слой и библиотеку, но разделить форму/просмотр по type: для checklist — краткие проверки; для case — предусловия, шаги и ожидаемые результаты. Уточнить правила преобразования checklist в case и истории версий. **Приёмка:** каждое представление показывает только применимые поля; переключение, сохранение, пустой список и старые записи не теряют данные. **Зависимость:** TC2.

### TC2. Изучить Test IT — выполнено как исследование

Официальные [создание рабочих элементов](https://docs.testit.software/user-guide/sections/create-work-items.html) и [сравнение типов](https://docs.testit.software/user-guide/sections/compare-work-item-types.html) подтверждают общую библиотеку типов, отсутствие ожидаемых результатов и предусловий у checklist и возможность преобразовать его в case. **Решение для VTPad:** взять различие полей как ориентир TC1; отдельные маршруты не следуют из исследования и выбираются по собственному UX. В roadmap этот исследовательский пункт можно закрыть после принятия дизайн-решения.

## 5. Defects Dashboard

### DD1. Дашборд связанных дефектов для Space — нет

**Основание:** текущие dashboard и `analytics/router.py` не имеют агрегатов связанных bugs. **Решение:** после DD4 добавить space-scoped выборку result↔bug и секцию dashboard со счётчиками, списком и переходами в bug/result. **Приёмка:** числа воспроизводятся из связей только своего space, пустой результат объяснён, чужие данные недоступны. **Зависимость:** DD4.

### DD2. Группировка и фильтр Open/Fixed/Reopen — частично

**Основание:** `bug/enum.py` содержит эти статусы и другие; общая `BugsDataTable.vue` уже фильтрует статус. **Решение:** применить к связанным дефектам DD1 с отдельным счётчиком `Other` для CLOSED/HOLD/READY; повторно привязанный bug считать один раз в общей цифре. **Приёмка:** групповые счётчики и выборка фильтра совпадают, каждый существующий статус виден. **Зависимость:** DD1.

### DD3. Статистика дефектов по run и suite — нет

**Основание:** в `AnalyticsService` нет bug-агрегатов. **Решение:** определить атрибуцию suite для plan/multi-suite run по snapshot кейса; считать уникальные bugs и связи отдельно, добавить API и drill-down. **Приёмка:** одинаковый bug в двух результатах не удваивает общий итог; метрика по run/suite сверяется с исходными связями, старые run без snapshot помечены. **Зависимость:** DD4.

### DD4. Автоматическая связь bug с failed result — частично

**Основание:** quick bug flow создаёт bug и вторым запросом пишет `linked_bug_ids`, но `_serialize_result` в `test_run/service.py` не возвращает это поле, хотя UI его читает. **Решение:** первым исправлением вернуть связи в detail и проверить reload; затем сделать атомарный серверный create-and-link с проверкой space, idempotency и выбором уже существующего bug. «Автоматическая связь» означает связь после явного создания/выбора bug, а не автоматическое создание дефекта на каждый fail. **Приёмка:** связь видна после reload; сбой не оставляет созданный bug без связи; чужой bug и повтор не создают некорректных ссылок.

## 6. Global UX

### UX1. Cmd/Ctrl+S и Esc — частично

**Основание:** Cmd/Ctrl+K есть, Escape в `App.vue` закрывает scrim, редактор сохраняется кнопкой. **Решение:** контекстный save shortcut активной формы с `preventDefault`, блокировкой повтора и учётом TipTap; Escape должен закрывать только верхний overlay с корректной обработкой несохранённых изменений. **Приёмка:** shortcuts работают на Mac/Windows, вложенных диалогах и после восстановления фокуса, не сохраняют чужую форму.

### UX2. Skeleton для таблиц — нет в основных списках

**Основание:** списки suites/cases/runs используют `v-data-table-server :loading`, skeleton есть лишь в Tech Docs. **Решение:** общий шаблон начальной загрузки с постоянной высотой строк, оставив фильтры доступными; повторную загрузку отмечать без резкого скачка. **Приёмка:** initial/refetch/error состояния различимы и объявляются screen reader.

### UX3. Empty states с действием — частично

**Основание:** отдельные `v-empty-state` уже есть, основные таблицы не имеют полного CTA. **Решение:** составить матрицу «пусто / нет совпадений / ошибка / нет прав» и для каждого списка выбрать действие Create/Clear/Retry, иконку или иллюстрацию. **Приёмка:** действие доступно только при нужных правах и корректно работает клавиатурой.

### UX4. Мобильная адаптация — частично

**Основание:** некоторые detail используют responsive grid, но table/toolbar и будущий split layout не проверены как целый сценарий. **Решение:** аудит ключевых маршрутов по viewport из `project-docs/docs/ops/ui-regression-full-checklist.md`, адаптация навигации, таблиц, редактора и диалогов. **Приёмка:** нет горизонтального переполнения, действия доступны касанием, zoom/reflow и фокус работают. **Зависимость:** SU1/SU3 учитывать в макете.

## 7. Backend and Data

### BD1. PostgreSQL full-text search (`tsvector`) — нет

**Основание:** поиск кейсов и Tech Docs использует `icontains`; semantic search решает другую задачу. **Решение:** определить поля, язык и поведение поиска; миграцией заполнить `tsvector` и GIN индекс, использовать параметризованный `websearch_to_tsquery`, ранжирование и стабильную пагинацию с фильтром space. **Приёмка:** релевантность на русском/английском контрольном наборе, корректность доступа и `EXPLAIN` на ожидаемом объёме. Сохранить fallback для пустого запроса.

### BD2. CSV/JSON импорт и экспорт suites/cases — нет

**Основание:** соответствующих REST маршрутов не найдено. **Решение:** описать версионированную схему с sections, версиями, ссылками и правилами конфликтов; сначала сделать экспорт, затем preview с ошибками по строкам и атомарный импорт через domain services. Ограничить размер, MIME, scope и права. **Приёмка:** round trip, дубликаты, неверные поля, чужой space и частичный сбой не портят данные. **Решения перед реализацией:** сохранять ли исходные IDs и импортировать ли историю версий.

### BD3. Полный CRUD Tech Docs — есть по коду

**Основание:** `tech_doc/router.py` содержит GET tree/list/id, POST, PATCH и DELETE; `techDocService.js` и UI используют их. Формальный CRUD-контракт уже есть, но пункт нельзя считать безопасно завершённым: маршруты проверяют bearer, но не membership space; `get_by_id` ищет только по id, create/update не подтверждают parent в том же space. **Решение:** добавить проверки доступа и дерева, затем независимую security review и интеграционные тесты на два spaces. После этого закрыть пункт без повторной реализации CRUD.

## 8. Analytics — Later

### AN1. Расширить аналитику — открыт продуктовый объём

**Основание:** `analytics/router.py` уже отдаёт space stats, top failed, trend и suite coverage; новая метрика в roadmap не названа. **Решение:** после DD1–DD3 выбрать 1–2 пользовательских вопроса, для каждого определить период, знаменатель, фильтры, обработку пропусков и drill-down. Затем API, индексы и UI. **Приёмка:** каждая метрика вычисляется на контрольных данных и ведёт к исходным записям; пустой интервал понятен. **Решение перед реализацией:** утвердить конкретные метрики.

### AN2. Анализ длительности и трендов — нет

**Основание:** `AnalyticsService.get_trend` считает статусы, но не время. **Решение:** после TE1–TE5 добавить ряды оценки, фактической суммы кейсов и активного времени таймера по space/периоду; `NULL` исключать из средних и показывать coverage измерений. **Приёмка:** графики и отклонение от оценки сходятся с деталями run, паузы исключены, старые записи не искажают среднее. **Зависимость:** модель времени.

## 9. Future Ideas

### FI1. Расширенные фильтры Test Plan — нет

**Основание:** `TestPlanModel` хранит suite/case IDs; tags/priority кейсов отсутствуют, custom fields не завершены в UI. **Решение:** после SU8/FI5 определить динамический набор фильтров (tags, priority, typed custom fields), предпросмотр подходящих кейсов и момент фиксации snapshot run. **Приёмка:** пересечение фильтров совпадает с предпросмотром и составом созданного run при неизменных данных; изменение полей после создания run не переписывает историю.

### FI2. Сравнение двух run — нет

**Основание:** у run/result уже есть snapshots, отдельного diff API/UI нет. **Решение:** сопоставлять по testcase ID с учётом версии, показывать добавленные/удалённые кейсы и изменившиеся статусы, комментарии и длительности; явно показывать разные источники suite/plan. **Приёмка:** удалённый или изменённый исходный кейс не ломает diff, два чужих space недоступны.

### FI3. CI/CD webhooks для автотестов — нет

**Основание:** `TestCaseModel.external_id` есть, ingestion маршрута нет. **Решение:** определить подписанный формат входящего события, integration token в scope space, idempotency key, сопоставление `external_id` с case/run и журнал ошибок. **Приёмка:** повторная доставка не создаёт дубликат, неизвестный ID и чужой space отклоняются, источник результата виден в UI.

### FI4. Матрица трассировки требований — частично

**Основание:** `traceability/router.py` и `TechDocContent.vue` уже связывают Tech Doc с test case; матрицы нет. **Решение:** определить, какие Tech Docs являются требованиями, затем построить таблицу requirement → cases → последний result/coverage с фильтрами и строками без покрытия. **Приёмка:** строки воспроизводятся из links, межпространственные связи запрещены, кейсы без результатов отображаются отдельно. **Зависимость:** security follow-up BD3.

### FI5. Пользовательские поля кейсов — частично

**Основание:** `custom_field` содержит CRUD/value API и модель `testcase`, есть экран настройки, но компонент значений не найден в страницах кейса. **Решение:** встроить typed values в view/edit, валидировать тип, принадлежность field и права на сервере, затем включить в фильтры. **Приёмка:** значение сохраняется после reload, неверный тип или чужое поле отклоняется, удалённая настройка не ломает старый кейс.

### FI6. Шаблоны кейсов — нет

**Основание:** отдельного template API/UI не найдено. **Решение:** template как набор полей и шагов, копируемый при создании кейса; хранить версию шаблона для происхождения, не связывать изменения шаблона с уже созданными кейсами. **Приёмка:** создать/отредактировать кейс из шаблона, затем изменить шаблон без изменения старого кейса.

### FI7. Уведомление о завершении run — нет

**Основание:** `TestRunService.complete` меняет статус, notification событий для run нет. **Решение:** определить получателей и настройки; публиковать событие только после успешного перехода в completed и обеспечить идемпотентность доставки. **Приёмка:** подписчик получает одну ссылку на доступный run, повтор complete не создаёт дубль, чужой пользователь не видит уведомление.

### FI8. Email-отчёты — нет

**Основание:** UI отчётов существует, доставки по email не найдено. **Решение:** определить формат и срез, получателей, ручную отправку или расписание, очередь и наблюдаемость ошибок; при генерации и отправке проверять доступ к space. **Приёмка:** письмо содержит только разрешённые данные, сбой доставки виден и повторяем, повтор не создаёт неожиданного дубля. **Решение перед реализацией:** ручная отправка или расписание в первом этапе.

### FI9. Публичные ссылки на run — нет

**Основание:** run API требует bearer; публичного route/token механизма нет. **Решение:** выделить read-only snapshot с ограниченным составом полей, непредсказуемым токеном, сроком действия и отзывом; скрыть персональные данные/вложения по явной политике. **Приёмка:** ссылка открывает только разрешённый срез без входа, после отзыва недоступна, менять run через неё нельзя. **Зависимость:** отдельное решение по раскрываемым данным и security review.
